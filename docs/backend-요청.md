# 백엔드 요청 목록

작성 2026-08-15 · 프론트

확정 시안(Figma `와이어프레임` 페이지)을 그대로 구현하면서 **현재 OpenAPI 계약으로는
저장하거나 받아올 수 없는 값**을 모은 문서입니다.

지금은 전부 프론트 로컬(`localStorage`)에 담아 화면만 완성해 둔 상태라,
새로고침·기기 변경·재설치에서 값이 사라집니다.

## 0. 먼저 봐 주세요 — 지금 기능이 막혀 있는 것

### 0-1. (결정됨) 비밀번호는 12자를 유지합니다 — 시안 문구 수정 필요

프론트는 계약대로 **12자 이상**으로 되돌렸습니다. 서버 변경은 필요 없습니다.

다만 확정 시안의 회원가입 화면(`22:12764`)에는 **`영문, 숫자, 특수문자 포함 8자 이상`**
이라고 적혀 있습니다. 화면 문구만 12자로 바꿔 두었으니 **시안도 함께 고쳐 주세요.**

프론트는 길이 외에 영문·숫자·특수문자 각 1자 이상도 검증합니다.
계약에는 이 규칙(`pattern`)이 없는데, 서버에서도 같은 규칙을 걸지 결정해 주세요.

### 0-2. VAPID 공개키 전달 경로

- **현재**: 없음
- **요청**: 환경변수로 받을 수 있게 값 전달 (또는 `GET /push-config` 같은 엔드포인트)

Web Push 구독은 `applicationServerKey` 없이는 **아예 만들 수 없습니다.**
`POST /push-subscriptions` 는 계약에 있지만, 그 앞에서 브라우저 구독을 만드는 단계가
키가 없어 막힙니다. 지금은 `VITE_VAPID_PUBLIC_KEY` 를 읽도록만 해 두고,
키가 없으면 알림 설정 UI 가 "준비 중" 상태로 빠집니다.

## 1. 회원가입 — 동의 항목 분리 (**최소한 필수/선택 구분은 필요**)

확정 시안의 `동의` 화면(`22:10802`)은 **세 항목**을 각각 받습니다.

| 화면 문구 | 필수 여부 |
| --- | --- |
| (필수) 개인정보 수집 이용동의 | 필수 |
| (필수) 서비스 이용약관 동의 | 필수 |
| (선택) 마케팅 정보 수신 동의 | **선택** |

현재 `OnboardingRequest` 에는 `sensitiveDataConsent: true` 하나뿐이라
세 항목을 구분해 남길 수 없습니다. 특히 **마케팅 동의는 선택 항목**이라
별도 필드가 없으면 "동의하지 않음"을 기록할 방법 자체가 없습니다.

요청:

```
consents: {
  privacy:   boolean   # 필수
  terms:     boolean   # 필수
  marketing: boolean   # 선택
}
```

동의 시각과 문구 버전도 항목별로 남을 수 있으면 좋겠습니다(개인정보 관련 감사 대응).

또 하나 — 시안에서 **동의는 회원가입 2단계**이고 버튼이 `가입하기` 입니다.
즉 계정 생성 시점에 동의가 이미 확정돼 있으므로, 동의를 `POST /users` 에서 함께 받는 쪽이
자연스럽습니다. 지금은 온보딩 API 로만 보낼 수 있어서, 프론트가 동의값을
온보딩 마지막까지 들고 갔다가 보내고 있습니다.

2026-08-15 기획 결정으로 **범위에서 빠졌습니다.** 요청하지 않습니다.

## 4. 기본 피부점호 시각 — `const` 해제

- **위치**: `NotificationSettings.time`
- **현재**: `{ const: '17:30' }`
- **요청**: `HH:mm` 문자열 + 사용자별 저장/수정

온보딩 마지막 화면(`22:12677`)이 **시각 선택 휠**입니다. 값을 고르게 해 놓고
저장이 안 되는 상태입니다.

부대마다 휴대전화를 받는 시간이 다릅니다(일과 후 사용은 보통 18:00~21:00이지만
근무 형태에 따라 편차가 큽니다). 이 값이 고정이면 알림 기능의 의미가 약해집니다.

`timezone` 은 `Asia/Seoul` 고정으로 두어도 무방합니다.

## 5. 알림 수신 여부의 의미

확정 시안의 온보딩 마지막 화면에는 **`알림 없이 시작하기` 갈래가 없습니다.**
그래서 프론트는 이렇게 처리하고 있습니다.

- 점호 시각을 고르고 `시작하기` → 브라우저 알림 권한 요청
- 권한 허용 → `notificationEnabled: true`
- 권한 거절 → `notificationEnabled: false` (가입은 그대로 진행)

이 해석이 기획 의도와 맞는지 확인 부탁드립니다.

## 6. 피부보고 선택지 어휘가 계약 enum 과 안 맞습니다

확정 시안의 피부보고1(`22:13847`)·피부보고2(`22:12586`)는 선택지가 **얼굴 그림 위 좌표**와
**타일 일러스트**에 묶인 고정 목록이 됐습니다. 그런데 그 목록이 계약 enum 과 1:1 이 아닙니다.

프론트는 `src/api/designOptions.ts` 한 곳에 화면 값 → 계약 값 표를 두고 제출 직전에 옮깁니다.
아래는 **옮기다가 정보가 사라지는 지점**입니다.

### 6-1. 부위 — 세 개가 `OTHER` 로 접힙니다

| 시안 칩 | 보내는 값 | 비고 |
| --- | --- | --- |
| 이마 | `CENTER_FOREHEAD` | 계약은 좌/중/우로 나뉘는데 시안은 하나 |
| 왼 볼 / 오른 볼 / 코 / 인중 | 그대로 | 정상 |
| **턱** | `OTHER` | 계약에 `LEFT_CHIN`·`RIGHT_CHIN` 뿐이라 좌우를 임의로 정할 수 없음 |
| **눈가** | `OTHER` | 대응 값 없음 |
| **관자놀이** | `OTHER` | 대응 값 없음 |

정보를 잃지 않으려고 `otherAreasNote` 에 한글 라벨을 함께 실어 보내고 있습니다.
요청: `CHIN`(가운데 턱), `EYE_AREA`, `TEMPLE` 추가.
반대로 계약에만 있는 `NECK`·`JAWLINE`·`WHOLE_FACE` 는 시안에 고를 자리가 없습니다.

### 6-2. 겉모습 — `OOZING` 을 고를 수 없어 진물 분기가 죽습니다

시안 타일은 여섯 장(붉은 반점·작은 돌기·털 주변 붉은 돌기·뾰루지·각질/건조·기타)뿐이라
계약의 `OOZING`(진물)과 `CRUST`(딱지)를 **고를 방법이 없습니다.**

`OOZING` 은 관리 전 확인(pre-care)에서 `PUS_OOZING_BLISTER` 를 미리 켜 주는 방아쇠입니다.
지금 상태로는 그 분기가 영영 안 켜집니다. 타일을 늘릴지, 분기를 다른 신호로 바꿀지 정해 주세요.

### 6-3. 상황 — 네 개가 전부 `OTHER` 로 뭉칩니다

시안 12종 중 **야외 활동 · 식습관 변화 · 스트레스 · 피부접촉 환경** 은 대응 값이 없어
모두 `OTHER` 로 갑니다. 서버는 이 넷을 구분하지 못합니다.
또 **훈련/운동** 과 **땀/과피지** 는 둘 다 `SWEAT_OR_DUST_AFTER_TRAINING` 이라 하나로 합쳐집니다.

요청: `OUTDOOR_ACTIVITY`, `DIET_CHANGE`, `STRESS`, `SKIN_CONTACT` 추가와
`SWEAT_OR_DUST_AFTER_TRAINING` 분리.

### 6-4. `현재 피부 상태` 는 `sensations` 와 다른 질문입니다

시안의 마지막 질문은 **건조함 / 유분많음 / 속건조,당김 / 민감함** 입니다.
계약의 `sensations`(가려움·따가움·눌렀을 때 통증·가만히 있어도 통증·열감·당김)와
겹치는 건 `TIGHTNESS` 하나뿐이고, 사실상 **피부 타입**을 묻고 있습니다.

지금 프론트는 이렇게 보냅니다.

- 건조함 · 속건조,당김 → `TIGHTNESS`
- **유분많음 · 민감함 → 보낼 곳이 없어 버려집니다**
- 옮길 게 하나도 없으면 최소 1개 제약 때문에 `NONE` 을 보냅니다
  (사용자가 `유분많음` 만 골라도 서버에는 "특별한 느낌 없음"으로 저장됩니다)

요청: `skinType` 같은 **별도 필드**로 받는 편이 맞다고 봅니다.
아니면 `sensations` enum 에 `OILY`·`SENSITIVE`·`DRY` 를 추가해 주세요.
지금은 사용자가 고른 값이 서버에 도달하지 않습니다.

### 6-5. (참고) 시안 아이콘이 모자랍니다 — 디자인 확인 필요

피부보고2 의 상황 타일 12개에 아이콘이 **다섯 종만** 있고 세 개씩 돌려 쓰고 있습니다
(땀/과피지 = 새 제품 사용 = 수면 부족, 식습관 변화 = 세안 지연 = 피부접촉 환경,
보호장비 착용 = 스트레스 = 피부 만짐). 시안 그대로 구현해 뒀지만 placeholder 로 보입니다.

## 7. 결과 화면 — 추천 성분과 항목 문구

### 7-1. `추천 성분` 필드가 없습니다 (지금 화면 값이 가짜입니다)

확정 시안의 결과 덱 다섯 번째 카드가 **`04 INGREDIENT GUIDE` / 추천 성분 보기** 입니다
(`22:12884`). 개편 전 `유사 기록 보기` 자리를 대체했습니다.

계약에 성분 필드가 없어서, 지금은 **시안에 적힌 세 줄(판테놀·세라마이드·마데카소사이드)을
`src/data/ingredients.ts` 에 그대로 박아 두고 있습니다.** 사용자의 기록과 무관한 고정값이라
실제 서비스에 그대로 나가면 안 됩니다.

요청: `careResult.ingredients` 추가.

```
ingredients: { name: string, effect: string, description: string }[]
```

`careResult.similarExperience` 는 시안에서 보여 줄 자리가 없어졌습니다.
지워도 되는지, 다른 곳에서 쓸지 알려 주세요.

> **기획·법무 확인 필요**: 성분 안내는 화장품법 제13조(부당한 표시·광고) 소지가 있습니다.
> 특정 제품 추천이 아니라 성분 정보 제공이라는 점, 효능을 단정하지 않는 문구인지
> 확인이 필요합니다. 지금 문구는 시안 그대로입니다.

### 7-2. 할 일 / 피할 일 / 확인할 변화 항목이 제목 + 설명 두 줄입니다

시안은 항목마다 **굵은 제목 한 줄 + 설명 한 줄**입니다.
(예: `새제품 피하기` / `새로운 제품을 추가하지 않고 기존 관리만 유지해주세요.`)

계약은 `doToday: string[]` 처럼 문자열 배열이라 이 두 줄을 나눌 수 없습니다.
지금은 첫 문장을 제목, 나머지를 설명으로 **추측해서** 나누고 있어서,
한 문장짜리 항목은 설명 없이 제목만 나옵니다.

요청: `{ title: string, description: string }[]` 로 내려주세요.

## 8. 경과 확인 — 의료진 분기에서 답이 하나 버려집니다

### 8-1. `관리 실행 정도`를 의료진 분기에서 받을 자리가 없습니다

확정 시안의 의료진 확인 화면(`22:10770`)은 **두 가지를 묻습니다.**

1. 기록 이후 의무실 또는 의료진에게 확인했나요? → `clinicianCheckStatus`
2. 안내받은 관리를 어떻게 실행했나요? → **담을 자리 없음**

계약의 `ClinicianFollowUpRequest` 는 `kind` · `skinChange` · `clinicianCheckStatus` 만 받습니다.
사용자가 2번에 답해도 서버에 도달하지 못하고 버려집니다.

요청: `ClinicianFollowUpRequest` 에도 `actionCompletion` 추가.
(셀프케어와 같은 값이라 `SaveFollowUpRequest` 공통으로 올려도 됩니다)

### 8-2. `SkinChange` 선택지가 다섯에서 셋으로 줄었습니다

시안은 **좋아졌어요 / 비슷해요 / 악화됐어요** 세 장뿐입니다.
계약의 `NEW_AREA`(새로운 부위)·`UNSURE`(잘 모르겠어요)는 고를 자리가 사라져 화면에서 뺐습니다.

enum 에서 지울지, 시안에 타일을 되살릴지 정해 주세요.
지금은 프론트가 세 값만 보냅니다.

### 8-3. (디자인 확인) `피부변화확인` 화면의 위치를 이렇게 봤습니다

`피부변화확인`(`22:13923`)은 피부 변화만 묻고 `다음` 으로 끝나는 화면입니다.
진입 경로가 시안에 없어서 **의료진 확인 분기의 첫 화면**으로 놓았습니다.

그렇게 본 이유는 이렇습니다 — 의료진 확인 화면에는 피부 변화를 묻는 자리가 없는데
계약은 `skinChange` 를 필수로 받습니다. 이 화면이 그 값을 채워 주는 앞 단계라고 보면
앞뒤가 맞습니다. 그래서 의료진 분기는 두 화면이 됐습니다.

```
셀프케어   : 오늘의 경과 확인 (표정 타일 + 관리 실행)          → 저장
의료진 확인 : 피부변화확인 (표정 타일) → 오늘의 경과 확인 (확인 여부 + 관리 실행) → 저장
```

이 순서가 아니라면 어디서 들어가는 화면인지 알려 주세요.

## 9. 기록조회·이력상세 — `트러블 하나를 여러 날 추적`하는 개념이 없습니다

확정 시안의 기록조회(`22:12795`)와 이력상세조회(`22:13739`)는
**보고 한 건**이 아니라 **트러블 하나를 여러 날에 걸쳐 따라가는 묶음**을 보여줍니다.

- 기록조회 상단 `이어서 확인할 기록` — 제목(`턱 턱선 트러블`), **시작일**, 최근 변화 한 줄
- 이력상세 `피부 변화 기록` — `2026.06.07(오늘)` / `2026.06.03(4일째)` / `2026.05.31(시작일)`
  세 시점이 한 타임라인에 쌓임

계약은 이렇게 되어 있습니다.

- 피부보고(`SkinReport`)는 **하루 한 건**이고 서로 이어져 있지 않습니다
- 경과(`FollowUp`)는 **보고당 한 번만** 남길 수 있습니다

그래서 시안의 타임라인을 채울 데이터가 없습니다. 지금 화면은 보고 한 건과
그에 달린 경과 한 건만 그리고 있어서, 시안처럼 여러 시점이 쌓이지 않습니다.
`시작일` · `N일째` · 트러블 제목도 만들 수 없습니다.

정해야 할 것:

1. 여러 날의 보고를 하나의 트러블로 묶는 개념을 만들지 (예: `troubleId`)
2. 묶는다면 누가 묶는지 — 사용자가 `이어서 기록하기`로 잇는지, 서버가 부위·겉모습으로 추정하는지
3. 트러블 제목(`턱 턱선 트러블`)을 누가 만드는지 (AI 요약인지 사용자 입력인지)
4. 한 트러블에 경과를 여러 번 남길 수 있어야 하는지 (지금은 보고당 1회 제한)

**이 그룹에서 가장 큰 공백입니다.** 나머지 항목과 달리 필드 몇 개 추가로 끝나지 않고
데이터 모델이 바뀝니다. 우선순위를 정해 주세요.

### 9-1. 설정의 여섯 항목은 갈 곳이 없습니다

설정(`22:10909`)의 `서비스` · `약관 및 개인정보` · `도움말` · `문의하기` · `고객지원` 은
연결될 화면이 시안에 없습니다. 없는 화면을 지어내지 않고 `준비 중` 으로 표시해 뒀습니다.
내용(약관 전문, 고객지원 채널)이 정해지면 열겠습니다.

## 10. 나머지

### 10-1. 월별 기록 수 집계

기록조회(`22:12795`)는 목록을 월 단위로 묶어 보여줍니다.
지금은 `GET /skin-reports` 로 **목록 전체를 받아 프론트에서 세고** 있습니다.
기록이 쌓일수록 첫 화면에서 수백 건을 받아야 하니 오래 쓸수록 느려집니다.

요청: 월별 건수를 따로 주세요. 예:

```
GET /skin-reports/monthly-counts
→ [{ month: '2026-08', count: 12 }, ...]
```

또는 목록 응답의 `pagination` 옆에 `totalCount` 만이라도 붙여 주세요.

### 10-2. 날짜별 점호 시각 예외

기본 점호 시각(4번)과 별개로, **특정 날짜만 다른 시각**으로 알림을 받는 요구가 있습니다
(당직·야외훈련 등으로 그날만 폰을 늦게 받는 경우).

지금은 저장할 곳이 없어 화면에도 넣지 않았습니다.
4번(기본 시각)이 먼저 열려야 의미가 있어서 **후순위**로 봅니다.

```
PUT /me/check-in-overrides/{date}   { time: 'HH:mm' }
DELETE /me/check-in-overrides/{date}
```

### STREAK — 값이 틀릴 수 있습니다

홈에 연속 기록일이 새로 들어왔습니다(`22:10680`). 계약에 필드가 없어서
프론트가 `GET /skin-reports?limit=30` 결과로 직접 세고 있습니다(`src/lib/streak.ts`).

**문제는 이 목록에 피부보고가 있는 날만 나온다는 점입니다.**
`괜찮아요`(`NO_DISCOMFORT`)만 누른 날은 `DailyCheckIn` 으로만 남고 목록에 없어서,
**성실하게 기록한 사용자의 연속이 중간에 끊긴 것처럼 보입니다.**
오늘 하루치는 홈이 주는 `today` 로 보정하지만 그 이전 날은 방법이 없습니다.

정해야 할 것:

1. `괜찮아요` 만 누른 날을 연속에 포함할지 (포함하는 게 맞다고 봅니다)
2. 하루 경계를 언제로 볼지 (Asia/Seoul 자정)
3. 30일보다 긴 연속을 어떻게 다룰지

**서버가 계산해서 `Home` 에 얹어 주는 쪽을 제안드립니다.** 예:

```
streak: { current: integer, recentDays: boolean[] }   # recentDays 는 최근 5일
```

`recentDays` 는 홈의 막대 그래프(`22:10691`, 막대 5개)에 그대로 씁니다.
이 필드가 생기면 프론트의 목록 재요청 한 번이 통째로 없어집니다.
